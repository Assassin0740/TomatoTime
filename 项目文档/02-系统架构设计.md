# 02 · 系统架构设计

> **本文目标**：说明系统的**结构、模块边界、接口契约与技术选型**，作为后续开发与评审的依据。
> 阅读前提：先读 [`01-系统运行原理.md`](./01-系统运行原理.md) 了解运行时行为。

## 1. 架构总览

采用 **Electron 经典三层结构**：主进程（Main）+ 两个独立渲染进程（Renderer），彼此通过 IPC 解耦。

```
┌────────────────────────────────────────────────────────────────┐
│                      应用层（用户可见）                          │
│  ┌───────────────────────┐        ┌───────────────────────┐    │
│  │   主窗口（管理台）      │        │   悬浮窗（挂件）        │    │
│  │   计时器.html           │        │   float.html           │    │
│  │   + renderer.js        │        │   HTML+CSS+JS 自包含    │    │
│  │   + style.css          │        │                        │    │
│  └───────────┬───────────┘        └───────────┬───────────┘    │
└──────────────┼────────────────────────────────┼────────────────┘
               │  ipcRenderer / webContents     │
┌──────────────▼────────────────────────────────▼────────────────┐
│                   主进程 main.js（中枢）                          │
│  ┌──────────┬──────────┬──────────┬──────────┬──────────────┐  │
│  │ 生命周期  │ 计时器    │ 窗口管理  │ 托盘     │ 文件 I/O      │  │
│  │ app.*    │ 状态机    │ BrowserW │ Tray     │ fs           │  │
│  └──────────┴──────────┴──────────┴──────────┴──────────────┘  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │            IPC 转发中枢（约 30 个 ipcMain 监听器）          │  │
│  └──────────────────────────────────────────────────────────┘  │
└──────────────────────────┬─────────────────────────────────────┘
                           │
┌──────────────────────────▼─────────────────────────────────────┐
│                        数据层                                    │
│  ┌──────────────────────┐       ┌──────────────────────────────┐ │
│  │ 渲染进程工作副本       │       │ 文件系统 <userData>/          │ │
│  │ localStorage（主窗口） │       │  ├ app-data.json  ← 权威副本  │ │
│  │ notes / archived_notes│──镜像─►│  ├ app-data.backup.json      │ │
│  │ + 约 28 个设置键       │       │  ├ floatWindowConfig.json    │ │
│  └──────────────────────┘       │  ├ CustomDraws/ NoteImages/  │ │
│        ▲ 由 store.js 读写         └──────────────────────────────┘ │
│        └─ 读取方：托盘 / 悬浮窗 / 后续的数据备份与移动端通道          │
└─────────────────────────────────────────────────────────────────┘
```

### 分层职责

| 层 | 职责 | 禁止事项 |
|---|---|---|
| 应用层（渲染进程） | UI 呈现、用户交互、DOM 操作 | ✗ 直接访问另一渲染进程<br>✗ 直接操作 fs（虽有权限，但破坏了架构边界） |
| 主进程 | 业务状态（计时器）、窗口生命周期、文件系统、IPC 转发 | ✗ 直接操作渲染进程的 DOM |
| 数据层 | 持久化 | —— |

### 2.1b 主进程存储模块 `store.js`（253 行）· 2026-09-11 新增

`main.js` 的伴生模块，把「任务 + 全部设置」集中到 `<userData>/app-data.json`。

| 能力 | 接口 | 说明 |
|---|---|---|
| 初始化 | `init()` | 定位文件、载入、生成上一会话备份、损坏文件留档 |
| 同步读 | `getItem(k)` / `getAll()` | 语义与 `localStorage.getItem` 一致 |
| 镜像写入 | `setItem(k,v,rev)` / `removeItem(k,rev)` / `clear()` | 由 preload 调用，180ms 合并落盘 |
| 全量导入 | `importAll(obj,rev)` | 首次迁移 + 每次启动自愈，立即落盘 |
| 启动快照 | `snapshot()` | 供 preload 判断导入 / 回填方向 |
| 退出落盘 | `flushSync()` | 在 `before-quit` 中调用 |
| 诊断 | `stats()` | 键数、字节数、被跳过的键 |

安全设计：原子写入（`.tmp` → rename）、损坏留档（`.corrupt-<时间>`）、单值上限 512 KB。

### 2.1c 渲染进程桥接 `preload.js`（181 行）· 2026-09-11 新增

只在**主窗口**生效（悬浮窗不参与，避免两窗口互相覆盖）。在页面脚本执行前：

1. `sendSync('store:snapshot')` 取主进程快照；
2. 按 `__store_rev` 序号决定方向 —— 主进程更新则留档后回填，本地领先或本地已空但主进程有数据则导入 / 恢复；
3. 用 `Object.defineProperty` 把 `window.localStorage` 换成镜像实现：写本地 + 发 `store:set`。

三条安全原则详见 [`01-系统运行原理.md`](./01-系统运行原理.md) §5.1。

### 2.3 悬浮窗 `float.html`（865 行，自包含）

| 功能 | 说明 |
|---|---|
| 时钟显示 | 接收 `timer-status` 渲染 MM:SS，支持字体大小 / 颜色 / 发光 / 阴影 |
| 任务区 | 显示当前任务文本 + 图片（受 `floatShowTask` / `floatShowImages` / `floatImageLimit` 控制） |

## 3. 接口契约

### 3.1 IPC 契约规范

所有 IPC 频道遵循以下命名与数据类型约定：

| 规则 | 说明 |
|---|---|
| 命名 | kebab-case，动词前置：`toggle-xxx`、`update-xxx`、`get-xxx`、`float-xxx` |
| 方向标注 | 渲染→主用 `ipcRenderer.send`（单向）；主→渲染用 `webContents.send`（单向广播） |
| 需返回值 | 用 `ipcRenderer.invoke` / `ipcMain.handle`（仅文件类操作） |
| 载荷类型 | 尽量传**基本类型或可结构化克隆的对象**；大文件走 `invoke` 返回路径，不传二进制本体 |

完整频道清单见 [`01-系统运行原理.md` §4](./01-系统运行原理.md#4-ipc-通信通路完整映射)。

### 3.2 关键数据契约

**`timer-status` 载荷**

```ts
{
  isRunning: boolean,    // timerInterval !== null
  isWorking: boolean,    // true = 工作阶段
  currentTime: number    // 剩余秒数
}
```

**`float-content-settings` 载荷**（悬浮窗内容开关）

```ts
{
  showTask: boolean,     // 是否显示任务区（默认 true）
  showImages: boolean,   // 是否显示任务图片（默认 true）
  imageLimit: number     // 最多显示几张图，1–6，默认 3
}
```

**任务对象 `Note`**

```ts
{
  id: number,            // 时间戳
  content: string,       // HTML 片段（可含 <img>）★ 禁止当纯文本处理
  done: boolean,
  p: 1 | 2 | 3,          // 优先级
  type: 'short' | 'long',
  comments: string[],
  ts: number,
  doneTime?: number
}
```

### 3.3 localStorage 键契约

新增设置项时的**固定流程**（缺一不可）：

```
① renderer.js：读取时给默认值
    localStorage.getItem('mySetting') ?? '默认值'
② 用户操作变更 → localStorage.setItem('mySetting', 值)
③ 若悬浮窗需要感知 → 在 pushXxx() 中主动推送
④ main.js 悬浮窗 ready-to-show → executeJavaScript 读取并 send 给悬浮窗
⑤ float.html 接收并应用
```

## 4. 关键设计与算法

### 4.1 计时器漂移补偿算法

**问题**：`setInterval` 在系统负载高或休眠唤醒后会累计误差。

**方案**：以真实时间戳为基准推进，而非按拍递减。

```js
let lastTime = Date.now();
setInterval(() => {
    const now = Date.now();
    const elapsed = Math.floor((now - lastTime) / 1000);
    if (elapsed >= 1) {
        currentTime -= elapsed;
        lastTime += elapsed * 1000;   // ★ 基准按"已扣除的整秒"前移，剩余零头留到下一拍
    }
}, 100);
```

### 4.2 原子写入（`saveFloatWindowConfig`）

**问题**：写配置时崩溃 / 断电会写坏 JSON，导致配置丢失。

**方案**：先写临时文件，再 `rename` 覆盖（`rename` 在同一分区下是原子操作）。

```js
fs.writeFileSync(configPath + '.tmp', JSON.stringify(newConfig));
fs.renameSync(configPath + '.tmp', configPath);   // 原子替换
// 失败降级：直接写入
```

### 4.3 图片内容寻址存储

**问题**：base64 图片直接存 localStorage 会导致存储膨胀、渲染卡顿。

**方案**：内容寻址（Content-Addressable Storage）——文件名即内容哈希。

```
base64 → SHA-256 → <userData>/NoteImages/img_<hash>.<ext>
```
- **天然去重**：同一张图无论粘贴多少次，只占一份空间
- **配套 GC**：`cleanup-unused-images` 扫描所有任务的 `content`，回收无人引用的文件

### 4.4 图片懒加载

```
lazyloadifyHtml(html)   将 <img src> 替换为占位图，真实地址存进 data-src
        +
bindSentinelObserver()  IntersectionObserver 监听哨兵元素
        ↓
图片进入视口 → 恢复真实 src → 触发加载
```
目的：即使任务列表有几百张图，首屏也只加载可见部分。

### 4.5 增量渲染

`render()` 用 `renderedCardCount` / `renderedArchiveCounts` 记账，只 `append` 新增卡片，不整体 `innerHTML = ''`。避免全量重绘导致的白屏与滚动抖动。

## 5. 技术选型说明

| 选型 | 选择 | 理由 | 风险 |
|---|---|---|---|
| 桌面壳 | Electron ^28.3.3 | 跨平台、Web 技术栈、生态成熟 | 体积大（安装包约 100MB+）、内存占用高 |
| 前端框架 | **无**（原生 JS） | 零构建、改完即生效、上手门槛低 | 3500+ 行单文件，缺少组件复用与状态管理 |
| UI 结构 | 原生 HTML + `contenteditable` | 直接可控的富文本编辑 | 需要手工处理粘贴、HTML 净化 |
| 样式 | 原生 CSS | 无预处理器依赖 | 1780 行，无命名空间隔离 |
| 持久化 | localStorage + 文件系统 | 轻量、无数据库依赖 | localStorage 有容量上限，无事务 |
| 打包 | electron-builder（NSIS） | 支持自定义安装目录 | 需手动重新构建才生效 |
| 富文本编辑 | `contenteditable` | 免引入编辑器库 | 各平台行为差异、HTML 脏数据需清理 |

## 7. 演进建议（架构级）

按投入产出比排序：

1. ~~**消除双 HTML 漂移**（低成本、高收益）~~ ✅ **已完成**（2026-09-11 删除 `index.html`）。
2. **抽取共享工具模块**（中成本、中收益）：把 `stripHtml` / 图片提取 / HTML 净化抽成公共文件，主窗口与悬浮窗共用。
3. ~~**设置集中化**~~ ✅ **已完成**（2026-09-11，`store.js` + `preload.js`：主进程持有全量副本，同步读取；详见 §2.1b/2.1c）。
   *剩余*：渲染进程仍以 localStorage 为工作副本，若要支持「外部写入反推界面」（如手机端远程改任务），需再加一条主进程 → 渲染进程的推送通道。
4. **渲染进程模块化**（高成本、高收益）：用原生 ES Module 拆分 `renderer.js`，无需引入打包工具即可实现。
5. **安全加固**（中成本、高收益）：`preload` 已存在（但目前只做存储桥接，且 `contextIsolation` 仍为 `false`）；下一步是开启 `contextIsolation` + `contextBridge`，替代裸 `require`。
6. **自动化测试**（中成本、高收益）：优先覆盖计时器状态机、任务 CRUD、图片保留三块核心逻辑。

## 8. 部署与运行

| 场景 | 命令 / 操作 | 说明 |
|---|---|---|
| 开发运行 | `npm start`（等价 `electron .`） | 直接运行源码 |
| 打包 | `npm run build` | electron-builder 生成 NSIS 安装包到 `dist/` |
| 产物 | `dist/` 下的 `.exe` | 用户实际安装的版本 |
| 用户数据目录 | `app.getPath('userData')` | Windows 下通常为 `%APPDATA%/计时器` |

> **⚠️ 重要**：改的是源码（`main.js` / `renderer.js` / `*.html`），`npm start` 立刻生效；但如果用户平时用的是 `dist/` 里打包的程序，**必须重新 `npm run build` 才生效**。

### 无头环境下的调试参数

在无 GPU 的环境（如自动化测试、远程会话）中运行 Electron 会触发 GPU 进程 FATAL，需追加：

```
--disable-gpu --disable-gpu-compositing --disable-software-rasterizer --in-process-gpu
```

如需查看渲染进程的 `console` 输出，还需设置环境变量 `ELECTRON_ENABLE_LOGGING=1`。
