# 01 · 系统运行原理

> **本文目标**：只读这一篇，就能理解"这个程序是怎么跑起来的"——从双击图标到关闭退出，每个环节发生了什么。
> 涉及文件：`main.js`、`renderer.js`、`计时器.html`、`float.html`

---

## 1. 三个运行实体

这个应用由 **3 个相互独立的运行单元** 组成，它们之间不直接对话，全部通过主进程转发：

| 运行单元 | 载体 | 职责 | 说明 |
|---|---|---|---|
| **主进程** | `main.js` | 应用生命周期、托盘、**计时器状态机**、悬浮窗窗口管理、文件读写、IPC 转发中枢 | 整个应用的"大脑"，即使窗口全部隐藏也在运行 |
| **主窗口渲染进程** | `计时器.html` + `renderer.js` + `style.css` | 任务增删改查、列表渲染、设置面板、导入导出 | 用户的主要操作界面 |
| **悬浮窗渲染进程** | `float.html`（自包含） | 常驻桌面显示剩余时间 / 当前任务 / 任务图片，支持在窗内完成任务与编辑 | 独立窗口，与主窗口无直接通信 |

```
        ┌──────────────────────────────────────────────┐
        │           主进程 main.js（大脑）               │
        │  ┌────────────┐  ┌──────────┐  ┌───────────┐ │
        │  │ 计时器状态机 │  │ 托盘 Tray │  │ 文件 I/O  │ │
        │  └────────────┘  └──────────┘  └───────────┘ │
        │        ▲              ▲             ▲        │
        │        └──── IPC 转发中枢（ipcMain）──┘        │
        └───────┬──────────────────────────────┬───────┘
                │  webContents.send           │  webContents.send
                │  ◄── ipcRenderer.send ──     │  ◄── ipcRenderer.send ──
        ┌───────▼────────┐            ┌────────▼─────────┐
        │ 主窗口渲染进程   │            │ 悬浮窗渲染进程    │
        │ 计时器.html     │            │ float.html       │
        │ renderer.js     │            │ （自包含）        │
        └────────────────┘            └──────────────────┘
                 ✗ 两个渲染进程之间不直接通信 ✗
```

> **为什么计时器放在主进程？**
> 如果计时器跑在渲染进程，页面被隐藏（最小化到托盘）时浏览器内核会节流 `setInterval`，计时会变慢甚至停摆。放在主进程就完全不受影响。

## 2. 启动流程（从双击到可交互）

```
双击图标 / npm start
        │
        ▼
① 单实例锁     app.requestSingleInstanceLock()
        │      已有一个实例在跑？→ 直接退出，并让已运行的窗口置前
        ▼
② app.whenReady()
        │
        ├──► store.init()    载入主进程集中存储（<userData>/app-data.json）
        │        └─ 必须先于窗口创建：preload 会立刻同步来取快照
        │
        ├──► createWindow()  创建主窗口（900×800，默认最大化）
        │        └─ loadFile('计时器.html')          ← 注意：加载的是"计时器.html"
        │        └─ ready-to-show → mainWindow.show()
        │        └─ 注册 close 事件（弹「最小化到托盘 / 退出应用」对话框）
        │        └─ 注册 F11 全屏、应用菜单（窗口/帮助）
        │
        ├──► createTray()    创建系统托盘（图标：图标/dstuy-bkp5e-001.ico）
        │        └─ 左键：显示/隐藏主窗口
        │        └─ 右键：弹出菜单（显示主窗口 / 开始暂停 / 切换模式 / 悬浮窗…）
        │
        └──► 注册全部 ipcMain 监听器（约 30 个）

③ 渲染进程加载（主窗口）
        │
        ├─ 读取 localStorage：notes / archived_notes + 约 28 个配置键
        ├─ migrateBase64Notes()      → 把历史遗留的 base64 图片迁移成文件
        ├─ migrateContentImages()    → 把任务 HTML 里的图片迁到 NoteImages/
        ├─ initBgImages()            → 加载背景图
        ├─ render()                  → 渲染任务列表
        └─ 绑定所有按钮事件
```

**启动时序上的一个隐患**：`renderer.js` 中的变量（如 `currentFilter`、`sortDirections`、`dateFilterMode`）曾被提升到脚本顶部以规避 *TDZ（暂时性死区）* 报错——历史提交 `942f869`、`cab85f4` 都是在修这类启动即崩的问题。修改脚本时**不要随意调整顶层 `let/const` 的位置**。

## 3. 计时器状态机（核心机制）

计时器是应用的心脏，实现在 `main.js` 的 `toggleTimer()` 中。

### 3.1 状态变量

| 变量 | 含义 | 初值 |
|---|---|---|
| `timerInterval` | `setInterval` 句柄；`null` 表示**未运行** | `null` |
| `currentTime` | 当前剩余**秒数** | `25 × 60` |
| `isWorking` | `true` = 工作中，`false` = 休息中 | `true` |
| `WORK_TIME` | 工作阶段总时长（秒），可配置 | `25 × 60` |
| `REST_TIME` | 休息阶段总时长（秒），可配置 | `10 × 60` |

> **判断计时器是否在运行**的统一标准是 `timerInterval !== null`（见 `getTimerStatus()`），而不是 `isTimerRunning`。

### 3.2 心跳与漂移补偿

```js
timerInterval = setInterval(() => {
    const now = Date.now();
    const elapsed = Math.floor((now - lastTime) / 1000);
    if (elapsed >= 1) {
        currentTime -= elapsed;
        lastTime += elapsed * 1000;   // 关键：用真实时间推进基准，而不是每拍 -1
        ...
    }
    broadcastTimerStatus();           // 每 100ms 广播一次最新状态
}, 100);
```

**设计要点**：每 100ms 检查一次，但**扣除的是真实流逝的秒数**，而不是简单地每拍减 1。这样即使系统卡顿、休眠唤醒，累计误差也会被自动补偿，不会越跑越慢。

### 3.3 状态迁移

```
        用户点「开始」
             │
             ▼
     ┌───────────────┐   currentTime 归零    ┌───────────────┐
     │   运行中       │ ───────────────────► │  阶段切换      │
     │ RUNNING       │   ① 发 timer-end      │ isWorking 取反 │
     └───────────────┘      （先发后切）      │ currentTime   │
             │  用户点「暂停」                │  = 新阶段时长  │
             ▼                               └───────┬───────┘
     ┌───────────────┐                               │
     │   暂停/停止    │ ◄─────────────────────────────┘
     │ STOPPED       │        （切完即暂停，等待用户再次开始）
     └───────────────┘
```

**关键顺序**：归零时**先发送 `timer-end` 通知**（携带的是"刚结束的阶段"），**再**切换 `isWorking`。若顺序写反，渲染进程会播放错误的提示音（工作结束却响休息音）。

### 3.4 阶段结束的副作用

| 副作用 | 实现位置 |
|---|---|
| 主窗口播放提示音 | `main.js` 发 `timer-end` → `renderer.js` 的 `playEndSound()` |
| 提示音按阶段选择 | 工作中结束 → `仕事終わったよ.wav`；休息中结束 → `休憩終わったよ.wav` |
| 刷新托盘菜单文字 | `main.js` 的 `updateTrayMenu()` |
| 广播最新状态到两个窗口 | `broadcastTimerStatus()` |

### 3.5 状态广播

```js
function broadcastTimerStatus() {
    const status = getTimerStatus();   // { isRunning, isWorking, currentTime }
    mainWindow.webContents.send('timer-status', status);
    floatWindow.webContents.send('timer-status', status);   // 悬浮窗同步
}
```
主窗口与悬浮窗共用同一条广播，因此**两处显示的时间天然一致**，不存在各自计时导致的偏差。

## 4. IPC 通信通路（完整映射）

通信原则：
- **渲染进程 → 主进程**：`ipcRenderer.send(频道, 数据)`
- **主进程 → 渲染进程**：`webContents.send(频道, 数据)`
- **渲染进程 ↔ 渲染进程**：❌ 禁止；必须先发到主进程再转发

### 4.1 计时器相关

| 频道 | 方向 | 作用 |
|---|---|---|
| `timer-status` | 主 → 全部窗口 | 广播 `{isRunning, isWorking, currentTime}` |
| `timer-end` | 主 → 主窗口 | 阶段结束，触发提示音 |
| `get-timer-status` | 渲染 → 主 | 主动拉取当前状态（窗口初始化时用） |
| `toggle-timer` | 渲染 → 主 | 开始 / 暂停（悬浮窗右键菜单也走这条） |
| `toggle-mode` | 渲染 → 主 | 在工作 / 休息之间切换 |
| `set-timer-time` | 渲染 → 主 | 设置本次倒计时时间 |
| `save-default-time` | 渲染 → 主 | 保存默认工作时长 / 休息时长 |
| `timer-running` | 渲染 → 主 | 上报计时器运行态（用于托盘菜单） |

### 4.2 悬浮窗相关

| 频道 | 方向 | 作用 |
|---|---|---|
| `toggle-float-window` | 渲染 → 主 | 打开 / 关闭悬浮窗 |
| `close-float-window` | 渲染 → 主 | 关闭悬浮窗 |
| `sync-notes-to-float` | 渲染 → 主 → 悬浮窗 | 主窗口把任务列表推给悬浮窗 |
| `request-notes-from-float` | 悬浮窗 → 主 → 主窗口 | 悬浮窗请求最新任务 |
| `float-toggle-done` | 悬浮窗 → 主 → 主窗口 | 在悬浮窗里打勾完成任务 |
| `float-edit-note` | 悬浮窗 → 主 → 主窗口 | 在悬浮窗里编辑任务内容 |
| `float-add-note` | 悬浮窗 → 主 → 主窗口 | 在悬浮窗里新增任务 |
| `toggle-float-lock` / `get-float-locked` | 双向 | 锁定 / 穿透悬浮窗（锁定后点击穿透到下层窗口） |
| `float-mousedown/mousemove/mouseup` | 悬浮窗 → 主 | 自定义拖拽（换算为窗口移动） |
| `show-float-menu` | 悬浮窗 → 主 | 弹出悬浮窗右键菜单 |

### 4.3 悬浮窗样式与内容同步

| 频道 | 方向 | 同步的内容 |
|---|---|---|
| `timer-color-update` | 主 → 悬浮窗 | 时间数字颜色 |
| `shadow-style-update` / `update-float-shadow-color` / `update-float-shadow-size` | 主 → 悬浮窗 | 阴影颜色与大小 |
| `glow-enabled-update` / `glow-color-update` / `glow-intensity-update` | 主 → 悬浮窗 | 发光开关 / 颜色 / 强度 |
| `float-content-settings` | 主 → 悬浮窗 | **`{showTask, showImages, imageLimit}`** —— 是否显示任务、是否显示任务图片、图片数量上限 |

### 4.4 设置的推送链路（重要模式 · 2026-09-11 重构）

设置项的**权威副本在主进程**（`store.js` → `<userData>/app-data.json`），渲染进程仍以
localStorage 作为工作副本，由 `preload.js` 把每一次写入镜像过去。于是推送悬浮窗时
不必再绕回主窗口：

```
用户改设置
        │
        ▼
主窗口 localStorage.setItem('xxx', 值)
        │
        ├──►（preload 替身）ipcRenderer.send('store:set', …) → 主进程 store 更新
        └──► 原有 IPC 频道直接把值 send 给悬浮窗

悬浮窗 ready-to-show
        │
        ▼
main.js pushSettingsToFloatWindow()
        └─ store.getItem('xxx')      ← 同步读取，完全不依赖主窗口
        │
        ▼
floatWindow.webContents.send('xxx-update', 值)
```

`timerColor` / `shadowColor` / `shadowSize` / `glow*` / `floatShow*` **全部走这条链路**。

**为什么这次要改**：重构前这里是 5 段
`mainWindow.webContents.executeJavaScript("localStorage.getItem('xxx')")` —— 异步、
强依赖主窗口存活、时序脆弱（问题 TD-06 / R-10）。现在主进程自己就持有数据，
读取变成同步，**即使主窗口已经关闭也能正确取到值**。

新增悬浮窗设置项时仍需改两处：主窗口写入 `localStorage` +
`pushSettingsToFloatWindow()` 里加一次 send。镜像到主进程由 preload 自动完成，不必手写。

### 4.5 文件 I/O（`ipcRenderer.invoke` / `ipcMain.handle`）

| 频道 | 作用 |
|---|---|
| `get-background-images` | 列出背景图 |
| `save-note-image` | 保存任务图片（base64 → 文件，按 SHA-256 去重命名） |

## 5. 数据存储设计

### 5.1 三层存储

| 层 | 位置 | 角色 |
|---|---|---|
| **localStorage** | 主窗口（Chromium 用户数据目录） | **渲染进程的工作副本**，界面所有读写都走它 |
| **主进程集中存储** | `<userData>/app-data.json` | **权威副本**，由 `store.js` 管理，供主进程 / 托盘 / 悬浮窗 / 将来的外部通道读取 |
| **文件系统** | `app.getPath('userData')` 下 | 图片文件 + 悬浮窗窗口配置（二进制与窗口状态，不进 JSON） |

```
<userData>/
├── app-data.json             # 任务数据 + 全部界面设置的集中副本（P2-3 新增）
├── app-data.backup.json      # 上一次会话开始前的快照（自动维护，可作还原点）
├── floatWindowConfig.json    # 悬浮窗位置 / 尺寸 / 是否带背景
├── CustomDraws/              # 用户自定义背景图
├── NoteImages/               # 任务内嵌图片（文件名 = SHA-256 哈希，天然去重）
└── （Electron 默认的 localStorage / Cache 等）
```

**同步机制**（`preload.js`，只在主窗口生效）

```
页面脚本执行前
        │
        ▼
sendSync('store:snapshot') 拿主进程快照
        │
        ├─ 主进程数据序号更新（storeRev > localRev）→ 留档后回填本地
        ├─ 本地已空但主进程有数据           → 从主进程恢复
        ├─ 序号相同 / 本地领先              → 以本地为准，导入刷新主进程副本
        └─ 装上 window.localStorage 替身：写本地 + 发 'store:set' 镜像
```

**三条不可动摇的安全原则**

1. **localStorage 永不被无条件覆盖**，只有「主进程明确更新」或「本地已空」才回填；
   回填前还会把现状写到 `localStorage-rescue-<时间>.json` 留档。
2. **写入顺序固定为「先 localStorage、后镜像」**——镜像失败只影响副本，不动数据。
3. **只有主窗口参与导入 / 回填**，悬浮窗不参与，避免两个窗口互相覆盖。

由此得到一个额外好处：**localStorage 被清空或损坏后，数据能从主进程副本自动恢复**。

**已知边界**：单个值超过 `512 KB` 时不进集中存储（`store.js` 的 `MAX_VALUE_BYTES`）。
目前只有悬浮窗配图 `floatImageData` 会命中——它是 data URL，可能有几 MB，
继续只存在于 localStorage。此规则同样作用于导入路径，不会把大值带进 JSON。

### 5.2 localStorage 键清单

**业务数据**

| 键 | 内容 |
|---|---|
| `notes` | 活跃任务数组（JSON） |
| `archived_notes` | 已归档任务数组（JSON） |

**界面与外观设置**

| 分类 | 键 |
|---|---|
| 计时器外观 | `timerColor`、`timerFontSize`、`shadowColor`、`shadowSize`、`glowEnabled`、`glowColor`、`glowIntensity`、`showModeLabel`、`modeLabelSize`、`cleanMode`、`pulseEnabled`、`cleanFontSize`、`normalFontSize` |
| 悬浮窗内容 | `floatShowTask`、`floatShowImages`、`floatImageLimit` |
| 背景 | `currentBgIndex`、`customBg`、`darknessLevel` |
| 列表视图 | `currentView`、`currentFilter`、`currentTypeView`、`sortDirections`、`containerWidth` |
| 其他 | `timerVolume` |

**内部键（由 preload 维护，业务代码不要碰）**

| 键 | 作用 |
|---|---|
| `__store_rev` | 单调递增的写入序号，双方据此判断谁的数据更新 |
| `__store_shim` | 标记 localStorage 替身已成功安装；缺失则下次启动走「强制导入」自愈 |

### 5.3 任务对象结构（Schema）

```js
{
    id: 1726032000000,        // 时间戳，同时用作唯一 ID
    content: '<div>写周报</div><img src="file:///…/NoteImages/img_ab12….png">',
                              // ★ HTML 片段，可含文字 + 图片
    done: false,              // 是否已完成
    p: 2,                     // 优先级：1=不紧急 2=中等 3=紧急
    type: 'short',            // 类型：'short'=短期 'long'=长期
    comments: [],             // 评论数组
    ts: 1726032000000,        // 创建时间戳
    doneTime: 1726035600000   // 完成时间戳（归档时补写）
}
```

> **⚠️ 最重要的约定**：`content` 是 **HTML 而不是纯文本**。任何"只处理文本"的代码路径（如旧的悬浮窗编辑逻辑）如果把 `content` 当纯文本回写，**任务里的图片会被永久删除**。改动任务内容相关逻辑时必须保留 `<img>` 标签。

### 5.4 图片生命周期

```
用户粘贴图片 / 导入表情
        │
        ▼
① 拿到 base64 → ipcRenderer.invoke('save-note-image', base64)
        │
        ▼
② 主进程计算 SHA-256 → 写入 <userData>/NoteImages/img_<hash>.<ext>
   （同图同哈希 → 天然去重，不重复占空间）
        │
        ▼
③ 返回 file:// 路径 → 写进任务的 content HTML
        │
        ▼
④ 删除任务时 → cleanup-unused-images 扫描全量任务，
   回收没有任何任务引用的图片文件（GC）
```

**懒加载机制**：任务列表渲染时，`lazyloadifyHtml()` 会把图片 `src` 换成占位图，并用 `IntersectionObserver` + 哨兵元素（sentinel）在图片进入视口时才真正加载，避免一次性加载大量图片导致卡顿（提交 `b285bc3` 的优化）。

## 6. 任务渲染管线

`render()` 是主窗口的核心，经历过多轮性能优化：

```
render(forceReset)
        │
        ├─ 按 currentView 分流 → 卡片视图 / 表格视图（renderTable）
        │
        ├─ 过滤：currentFilter（全部/未完成/已完成/紧急/中等/不紧急）
        │
        ├─ 类型过滤：currentTypeView（全部/短期/长期）
        │
        ├─ 日期范围：本周 / 全部时间 / 自定义
        │
        ├─ 排序：按 sortDirections（时间 / 紧急度 / 完成状态）
        │
        ├─ 增量渲染：只 append 新增的卡片 DOM，不再整体 innerHTML 重置
        │             （用 renderedCardCount / renderedArchiveCounts 记账）
        │
        └─ lazyloadifyHtml + bindSentinelObserver → 图片懒加载
```

**性能优化要点**：
- `render()` 采用**增量追加**而非全量重绘（提交 `1afa95b`）
- 图片使用 `IntersectionObserver` 懒加载，规避内存与滚动卡顿（提交 `b285bc3`）
- 曾修复"滚动触发渲染 → 渲染又触发滚动"的死循环（提交 `f7a27c7`）

## 7. 悬浮窗运行原理

悬浮窗是独立窗口，`float.html` 把 HTML/CSS/JS 全部塞在一个文件里。

### 7.1 窗口特性

| 属性 | 值 | 说明 |
|---|---|---|
| 尺寸范围 | 宽 150–700，高 50–250 | 三处校验必须一致，否则位置保存会失效 |
| 默认尺寸 | 380 × 100 | 见 `loadFloatWindowConfig()` |
| `transparent` | `true` + `opacity: 0.999` | **故意不设 1**：让 Chromium 走层合成渲染，规避 Windows DWM 画白条标题栏 |
| 置顶 | 默认 `alwaysOnTop = true` | 可切换 |
| 锁定 | `setIgnoreMouseEvents(true)` | 锁定后鼠标点击穿透到下层 |
| 任务栏 | `skipTaskbar: true` | 不在任务栏显示 |

### 7.2 任务显示与图片

```
主窗口 tasks 变化
        │  sync-notes-to-float
        ▼
主进程转发 → float.html 收到 currentNotes
        │
        ├─ 按 floatShowTask  → 决定整个任务区是否显示（关掉后只剩大时钟）
        ├─ 按 floatShowImages → 决定任务图片区是否显示
        └─ 按 floatImageLimit → 决定最多渲染几张图（1–6，默认 3）
                 │
                 ▼
        从 note.content 的 HTML 中提取 <img> 的 src，渲染为缩略图
        超出上限 → 显示 "+N" 角标
        点击图片 → 悬浮窗内临时放大 / 还原
```

### 7.3 悬浮窗内操作任务的回路

```
在悬浮窗打勾 / 编辑文字 / 新增
        │  float-toggle-done / float-edit-note / float-add-note
        ▼
主进程转发 → 主窗口 renderer.js 处理并写入 localStorage
        │
        ▼
主窗口重新 sync-notes-to-float → 悬浮窗刷新
```

> **编辑保图机制**：悬浮窗内编辑任务时，只替换文本部分，**保留原有 `<img>` 标签**（修复前的旧逻辑会用纯文本整体覆盖，导致图片丢失）。

## 8. 关闭与退出流程

```
点主窗口关闭按钮
        │
        ▼
mainWindow 'close' 事件
        │
        ├─ appIsQuitting == false → 弹对话框：
        │       「📥 最小化到托盘」→ mainWindow.hide()（计时器继续跑）
        │       「❌ 退出应用」    → appIsQuitting = true → app.quit()
        ▼
window-all-closed 事件
        │
        └─ 若 appIsQuitting == false → return（不退出，托盘常驻）
           若为 true → app.quit()

app.quit() → before-quit 事件
        ├─ store.flushSync()  ← 强制把最后一批写入落盘（平时是 180ms 合并写入）
        ├─ 销毁托盘 tray.destroy()
        └─ 依次关闭 floatWindow、mainWindow
```

**设计意图**：关闭窗口 ≠ 退出应用。默认行为是最小化到托盘，保证番茄钟在后台持续计时（这也是计时器放在主进程的原因之一）。

## 9. 关键设计决策速查

| 决策 | 为什么这么做 | 代价 |
|---|---|---|
| 计时器放主进程 | 不受页面隐藏时的定时器节流影响，后台也能精准计时 | 主进程承担业务逻辑，职责略重 |
| 渲染进程间不直连 | 统一由主进程转发，链路清晰可控 | 一次操作要经两跳 IPC |
| 数据集中到主进程 `app-data.json`（P2-3） | 主进程不再需要绕回主窗口取数据；为数据备份与移动端铺路 | 多一层镜像，需遵守三条同步原则 |
| localStorage 仍是渲染进程的工作副本 | 主进程副本失效时数据毫发无损，且浏览器能力（容量、原子性）保持不变 | 两处副本需靠序号机制保持一致 |
| 悬浮窗 `opacity: 0.999` | 规避 Windows DWM 白条标题栏 | 非直觉写法，容易被后人"修回去" |
| 图片存文件而非 base64 | 避免 localStorage 膨胀、渲染变慢 | 需要一套图片 GC 机制 |
| ~~`计时器.html` 与 `index.html` 双份~~ | ~~历史遗留~~ | ✅ **已消除**（2026-09-11 删除 `index.html`，主界面只有 `计时器.html` 一份） |
| 无前端框架、无构建 | 简单直接，改完即生效 | `renderer.js` 已 3500+ 行，维护成本高 |
