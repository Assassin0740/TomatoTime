### P0-2 消除双 HTML 漂移隐患（对应 `06` R-01）

**问题**：`main.js` 加载的是 `计时器.html`，但仓库中还存在内容一致的 `index.html`。两者必须手工同步，极易漂移。

**已验证的实际开销**：本次改动中就不得不额外执行 `cp 计时器.html index.html` 并做 `md5sum` 校验。

**推荐方案（方案 A）**：

1. 全仓搜索对 `index.html` 的引用（`main.js`、打包配置、脚本）
2. 确认无引用后删除 `index.html`
3. 在 `README.md` 与 `02-系统架构设计.md` 中明确"主界面源文件只有 `计时器.html`"

**备选方案**：保留文件但增加构建 / 提交前的一致性校验脚本。

| 项 | 评估 |
|---|---|
| 工作量 | 小（<1 小时，含引用排查） |
| 风险 | 低（需确认无外部引用） |
| 收益 | 高 —— 彻底消除一类"改了没生效"的困惑 |

### P1-3 抽取主窗口与悬浮窗的共享工具模块（对应 `06` R-11）

**问题**：主窗口与悬浮窗各自实现了一套任务内容解析（HTML 处理、图片提取、纯文本转换）。格式一旦变更，必须同时改两处——本次改动就遇到了这个问题（`stripHtml` 在 `float.html` 中单独实现）。

**方案**：新建 `note-utils.js`，导出：

```js
// 从 content HTML 中提取文本
function extractText(html) { ... }
// 从 content HTML 中提取图片 src 列表
function extractImages(html) { ... }
// 从一个 content 中取出文本部分而保留图片（编辑保图的核心）
function replaceTextKeepImages(html, newText) { ... }
// 基础的 HTML 净化（移除 script / on* 事件属性）
function sanitizeHtml(html) { ... }
```

由于两个渲染进程都开启了 `nodeIntegration`，可直接用 `require('./note-utils.js')` 引入，无需构建工具。

> **注意**：`float.html` 是自包含文件，引入外部脚本需新增 `<script src>`。若坚持自包含，可考虑在构建时内联。

| 工作量 | 风险 | 收益 |
|---|---|---|
| 中 | 中（需回归两端任务操作） | 高（消除双端同步成本与漂移风险） |

## 三、P2 · 中期结构性改进

### P2-1 渲染进程安全加固（对应 `06` R-02）

**问题**：两个渲染进程均开启 `nodeIntegration: true` + `contextIsolation: false` + `webSecurity: false`，渲染进程可直接 `require('fs')` 读写任意本地文件。

**方案**：

```
① main.js 创建窗口时改为：
     contextIsolation: true
     nodeIntegration: false
     sandbox: true
     preload: path.join(__dirname, 'preload.js')

② 新建 preload.js，用 contextBridge 按需暴露 API：
     contextBridge.exposeInMainWorld('api', {
        send: (channel, data) => { /* 白名单校验后 ipcRenderer.send */ },
        invoke: (channel, data) => { /* 白名单校验后 ipcRenderer.invoke */ },
        on: (channel, cb) => { /* 白名单校验后 ipcRenderer.on */ }
     });

③ 渲染进程把 ipcRenderer.xxx 全部替换为 window.api.xxx
```

**难点**：`renderer.js` 中大量直接使用 `require('electron')` 与 `ipcRenderer`，替换面较广；`float.html` 同样。

| 工作量 | 风险 | 收益 |
|---|---|---|
| 中—大 | 中（改动面广，需完整回归） | 高（消除安全债务） |

---

### P2-2 `renderer.js` 模块化拆分（对应 `06` R-03）

**问题**：单文件 3,569 行，职责混杂，修改易引发连锁回归。

**方案**：用**原生 ES Module**（无需打包工具）按功能拆分：

```
renderer.js            →  入口，负责初始化与组装
├── modules/
│   ├── timer-ui.js        计时显示与交互
│   ├── notes.js           任务 CRUD
│   ├── render-card.js     卡片视图渲染
│   ├── render-table.js    表格视图渲染
│   ├── filters.js         排序 / 筛选 / 日期范围
│   ├── archive.js         归档
│   ├── images.js          图片与背景
│   ├── settings.js        设置面板
│   └── storage.js         持久化封装
```

**难点**：需要处理跨模块共享状态（`notes`、`currentFilter` 等）；HTML 中大量 `onclick="window.xxx()"` 需逐个改为 `addEventListener` 或显式挂载到 `window`。

**建议**：**增量拆分**，每次只搬一个功能区，拆完立即回归验证。

| 工作量 | 风险 | 收益 |
|---|---|---|
| 大 | 中—高 | 高（长期可维护性） |

### P2-3 设置集中化（对应 `06` R-10）

**问题**：设置存在主窗口 localStorage，悬浮窗需要通过"主进程 `executeJavaScript` 读取 + 推送"的迂回方式获取，异步时序脆弱，新增设置项必须改三处。

**方案**：

```
① 所有设置统一存到主进程：<userData>/settings.json（沿用原子写入）
② 新增统一 IPC 通道：
     'get-settings'   渲染 → 主（invoke，返回全部设置）
     'set-setting'    渲染 → 主（写入并广播）
     'settings-changed' 主 → 全部窗口（广播）
③ 主窗口与悬浮窗启动时都主动拉取，之后靠广播同步
```

| 工作量 | 风险 | 收益 |
|---|---|---|
| 中 | 中（需处理迁移：从 localStorage 读到 settings.json） | 高（彻底解决双端同步问题） |

### P2-5 数据备份机制（对应 `06` R-12）

**问题**：任务数据仅在 localStorage，无自动备份。

**方案**：

| 方案 | 说明 |
|---|---|
| A | 应用启动时把当前数据写一份到 `<userData>/backup/`，保留最近 N 份 |
| B | 定期（如每周）提示用户导出 JSON |
| C | 每次归档操作时自动导出一份快照 |

**推荐**：A + C 组合，成本低且覆盖主要风险场景。

| 工作量 | 风险 | 收益 |
|---|---|---|
| 小—中 | 低 | 中—高（数据安全） |

## 七、明确不建议做的事

| 事项 | 不做的理由 |
|---|---|
| 引入 React / Vue 等前端框架 | 会引入构建流程，与当前"改完即生效"的开发体验冲突，收益不抵成本 |
| 引入 Webpack / Vite 等打包工具 | 同上；模块化用原生 ES Module 即可满足 |
| 引入数据库（SQLite 等） | 数据量级远未到需要数据库的程度，localStorage + 文件已足够 |
| 做云同步 / 账号体系 | 明确在范围外 |
| 全量重写 | 现有代码已稳定运行并通过验证，重写会引入大量新缺陷而无对应收益 |
