### P1-4 「阴影大小」改为真正的文字阴影（对应 `06` I-02）—— ✅ 已完成

**实施结果（2026-09-11）**：改为 CSS 变量 `--text-shadow` + `text-shadow`，并与"发光"效果**叠加**而非互相覆盖：

```css

#time.glow                   { text-shadow: var(--text-shadow, ...), 0 0 var(--glow-intensity) var(--glow-color), ...; }
body:not(.with-background) #time.glow { text-shadow: var(--text-shadow, ...), 0 0 5px rgba(0,0,0,.9), ...; }
```

原先顾虑的"文字阴影与发光打架"通过**叠加**解决，不需要取舍。

## 三、P2 · 中期结构性改进

### P2-1 渲染进程安全加固（对应 `06` R-02）

**问题**：两个渲染进程均开启 `nodeIntegration: true` + `contextIsolation: false` + `webSecurity: false`，渲染进程可直接 `require('fs')` 读写任意本地文件。

**方案**：

```
① main.js 创建窗口时改为：
     contextIsolation: true
     nodeIntegration: false
     sandbox: true
     preload: path.join(__dirname, 'preload.js')

② 新建 preload.js，用 contextBridge 按需暴露 API：
     contextBridge.exposeInMainWorld('api', {
        send: (channel, data) => { /* 白名单校验后 ipcRenderer.send */ },
        invoke: (channel, data) => { /* 白名单校验后 ipcRenderer.invoke */ },
        on: (channel, cb) => { /* 白名单校验后 ipcRenderer.on */ }
     });

③ 渲染进程把 ipcRenderer.xxx 全部替换为 window.api.xxx
```

**难点**：`renderer.js` 中大量直接使用 `require('electron')` 与 `ipcRenderer`，替换面较广；`float.html` 同样。

| 工作量 | 风险 | 收益 |
|---|---|---|
| 中—大 | 中（改动面广，需完整回归） | 高（消除安全债务） |

### P2-2 `renderer.js` 模块化拆分（对应 `06` R-03）

**问题**：单文件 3,569 行，职责混杂，修改易引发连锁回归。

**方案**：用**原生 ES Module**（无需打包工具）按功能拆分：

```
renderer.js            →  入口，负责初始化与组装
├── modules/
│   ├── timer-ui.js        计时显示与交互
│   ├── notes.js           任务 CRUD
│   ├── render-card.js     卡片视图渲染
│   ├── render-table.js    表格视图渲染
│   ├── filters.js         排序 / 筛选 / 日期范围
│   ├── archive.js         归档
│   ├── images.js          图片与背景
│   ├── settings.js        设置面板
│   └── storage.js         持久化封装
```

**难点**：需要处理跨模块共享状态（`notes`、`currentFilter` 等）；HTML 中大量 `onclick="window.xxx()"` 需逐个改为 `addEventListener` 或显式挂载到 `window`。

**建议**：**增量拆分**，每次只搬一个功能区，拆完立即回归验证。

| 工作量 | 风险 | 收益 |
|---|---|---|
| 大 | 中—高 | 高（长期可维护性） |

### P2-3 设置集中化（对应 `06` R-10）

**问题**：设置存在主窗口 localStorage，悬浮窗需要通过"主进程 `executeJavaScript` 读取 + 推送"的迂回方式获取，异步时序脆弱，新增设置项必须改三处。

### M11 · 外部音乐控制集成

**目标**：在计时器内查看并控制正在播放的音乐，并与计时状态联动。

**技术选型：Windows 全局媒体控件（SMTC）**

| 维度 | 内容 |
|---|---|
| 原理 | 读 Windows 系统级媒体会话（`GlobalSystemMediaTransportControlsSessionManager`），等价于替用户按键盘上的媒体键 |
| 可读取 | 曲目标题、艺术家、专辑、封面缩略图、播放状态 |
| 可控制 | 播放、暂停、上一首、下一首、**进度跳转（拖动进度条）** |
| 通用性 | 所有注册了 SMTC 的播放器：网易云、QQ 音乐、Spotify、浏览器内的网页播放器 |
| 版权 | 不涉及 —— 不解析音频、不获取播放链接 |

> **需求确认（2026-09-11）**：用户明确要求音乐面板为**全套**——显示在播曲目（含封面）+ 上一首 / 下一首 + **进度条可拖动跳转**。
> **技术影响**：进度跳转（`TryChangePlaybackPositionAsync`）与读取播放进度（`GetTimelineProperties`）都要求能调用 WinRT 接口，**路径 c（仅发送媒体键）不可行**；需要在路径 a（常驻 PowerShell 桥接）与 b（N-API 原生模块）之间选择。若实测发现进度信息不稳定，退路是"只显示进度但不可拖动"，并需向用户说明。

**实现路径（需实测后定）**

| 路径 | 做法 | 取舍 |
|---|---|---|
| a. 常驻 PowerShell 桥接进程 | 借 WinRT 反射调用，主进程与子进程做 JSON 通信 | 零编译依赖；需维护子进程生命周期与通信协议 |
| b. Node 原生模块 / N-API addon | 直接调用系统 API | 性能最好；需针对 Electron ABI 重编译，升级 Electron 时成本高 |
| c. 仅发送媒体键 | 只做控制不做读取 | 最简单；拿不到曲目信息，体验不完整 |

**前置实测清单**

1. 网易云 PC 版是否向 SMTC 注册会话（在 Windows 音量面板能否看到媒体卡片）
2. SMTC 实际可读字段范围（标题 / 艺术家 / 封面预计可用；进度条不一定）
3. 桥接方案的资源占用与稳定性（常驻进程内存、崩溃恢复）

**界面落点**

| 位置 | 内容 |
|---|---|
| 主窗口独立「音乐」面板 | 当前曲目 + 封面 + 播放 / 暂停 / 上一首 / 下一首 + 进度 |
| 悬浮窗（可选） | 一行「歌名 - 歌手」，可选迷你控制按钮 |
| 设置面板 | 启用开关、是否在悬浮窗显示、联动开关 |

**联动规则（可配置，默认关闭）**

```
开始专注         →  播放 / 恢复播放
暂停 / 进入休息   →  暂停播放
计时结束         →  暂停播放（或保持）
```

**架构约定**

- 所有 SMTC 调用放在**主进程**；新建 `integrations/smtc.js` 适配器
- 渲染进程仅通过 IPC 收发，不直连第三方
- 沿用"主进程中转"的既有约定，两个渲染进程之间仍不直接通信

**明确不做**：接入网易云非官方接口（会员曲目拿不到直链、需维护登录 cookie、有风控、随网易云改动失效，且属逆向接口而非官方开放平台）；模拟客户端点击（客户端一更新即失效）。

| 工作量 | 风险 | 收益 |
|---|---|---|
| 中 | 中（依赖第三方播放器行为 + 桥接方案稳定性） | 高（贴合"专注 + 音乐"的核心场景） |

### M12 · 任务外发到 AI

**目标**：把一条任务一键送到 WorkBuddy 或其他 AI 工具。

#### M12-1 剪贴板 + 唤起目标软件（第一版）

流程：任务 → 格式化为提示词 → 写入剪贴板 → 唤起目标程序 → 用户按一下粘贴。

| 环节 | 实现 |
|---|---|
| 入口 | 任务卡片 / 悬浮窗新增「发送到…」 |
| 提示词模板 | 可配置，默认含任务内容 + 优先级 + 类型 + 创建时间 |
| 目标程序 | 可配置列表（可执行文件路径或 URL），用 `shell.openExternal` / `child_process.spawn` |
| 剪贴板 | Electron `clipboard.writeText` |

**优点**：对**任何**软件通用（不限于 AI），零依赖；"半自动"反而是优点 —— 提示词常需临场补充。

#### M12-2 直连 AI 接口做任务拆解（第二版，可选）

一条任务 → 调用模型 → 拆成若干子任务。

**关键约束**：AI 输出格式不稳定（可能夹杂解释、字段缺失），**必须先预览确认再写入列表**，禁止直接落库。

### M13 · 移动端（手机版）

> **首要认知：Electron 没有移动端运行时。** 现有代码无法直接打包成手机 App。
> 手机版是**另一条技术栈**，不是"顺手加个适配"。

#### 路线选择

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 局域网 Web 版** | 主进程内起 HTTP 服务（Node 原生 `http`，零依赖），手机浏览器访问 `http://<电脑IP>:<端口>` | 零安装、跨 iOS/Android、前端代码可复用、数据天然在电脑 | 需电脑开机且同一局域网；无系统级推送 |
| **B. PWA** | 在 A 之上加 `manifest` + Service Worker，手机「添加到主屏幕」 | 有图标、全屏无地址栏、可缓存 | **局域网 `http://` 下 Service Worker 与通知权限基本不可用**，需 HTTPS 环境；iOS 限制更多 |
| **C. 原生 / 跨平台 App** | Capacitor / React Native / Flutter 重写界面 | 真推送、后台计时、桌面小组件、锁屏实时活动 | 界面基本重写，工程量最大 |

**推荐路径**：**A → B**；C 仅在确认长期投入移动端后再评估。

> **用户倾向记录（2026-09-11）**：用户在讨论中倾向选择 **C（原生 / 跨平台 App）**。
> **需要在动手前对齐的现实**：C 的工程量与 A/B **不在一个量级**——界面基本要重写，且项目只有一名维护者。因此建议的执行顺序仍然是 **先 A（局域网 Web，成本最低、能最快验证"手机上用起来到底顺不顺手"）→ 再判断是否值得为 C 投入**。
> 若最终确认走 C，技术选型建议 **Capacitor**：可以复用现有 HTML/CSS/JS 的大部分逻辑，不像 React Native / Flutter 那样要求完全重写，是三条路里"复用度最高"的原生方案。
> **无论走哪条路，`P2-3`（数据集中化）都是硬前置**——见本节末。

#### 移动端适配工作量（以 A / B 路线为前提）

| 项 | 说明 |
|---|---|
| 响应式布局 | `style.css` 现为纯桌面布局（1,780 行），需补移动端断点 |
| 触摸交互 | hover 态 → 触摸反馈；**右键菜单必须换形态**（任务卡片与悬浮窗均依赖右键），改为长按菜单或滑出操作 |
| 输入体验 | 软键盘弹出时的布局与滚动；`contenteditable` 在移动端的已知差异 |
| 屏幕适配 | 安全区（刘海屏）、点击热区 ≥ 44px、字体缩放 |
| 形态重设计 | **悬浮窗概念在手机上不存在**，需重新设计（如底部常驻计时条） |
| 性能 | 现有"懒加载 + 增量渲染"需按移动端设备重新验证 |

#### 数据同步（移动端真正的难点）

| 方案 | 说明 | 取舍 |
|---|---|---|
| **局域网直连** | 手机连电脑的内网服务，数据只存在电脑 | 最简单，A 路线的天然形态；需电脑开机 |
| 文件同步 | 数据落成 JSON，走 WebDAV / 网盘 | 可离线；需处理冲突合并 |
| 云后端 | 自建服务 | **明确不做**（见第八节） |

#### 「弹窗 / 提醒」的能力边界（重要）

| 形式 | 可行性 |
|---|---|
| 页面内提醒（App 打开时） | ✅ 一定能做 |
| Web 通知（Notification API） | ⚠️ 局域网 `http://` 下不可用，需 HTTPS |
| Web Push | ❌ 局域网环境下不可用 |
| 系统级推送 | ❌ 需原生 App，或借道第三方（Bark、微信服务号等） |
| **桌面端负责提醒** | ✅ **推荐** —— 提醒交给电脑端，手机端只做查看与记录 |

**定位建议**：桌面端 = 计时主场 + 提醒；移动端 = 查看任务 + 快速记录 + 远程控制。

#### ⚠️ 硬前置依赖

1. **数据集中化（`P2-3`）** —— 数据必须从主窗口 localStorage 迁到主进程管理的 JSON 文件。否则手机端**读不到任何数据**，这是移动端的硬前置。
2. **前端模块化（`P2-2`）** —— 一套代码同时适配桌面与移动，单文件 3,569 行会失控。

| 工作量 | 风险 | 收益 |
|---|---|---|
| 大 | 高（跨设备、跨平台、数据一致性） | 高（使用场景从"坐在电脑前"扩展到"随时"） |

## 八、明确不建议做的事

| 事项 | 不做的理由 |
|---|---|
| 引入 React / Vue 等前端框架 | 会引入构建流程，与当前"改完即生效"的开发体验冲突，收益不抵成本 |
| 引入 Webpack / Vite 等打包工具 | 同上；模块化用原生 ES Module 即可满足 |
| 引入数据库（SQLite 等） | 数据量级远未到需要数据库的程度，localStorage + 文件已足够 |
| 做云同步 / 账号体系 | 明确在范围外。**移动端（M13）用局域网直连，不引入云后端** |
| 用 Electron 打包移动端 | Electron 无移动端运行时，技术上不可行 |
| 为移动端用 React Native / Flutter 重写 | 仅当 C 路线被确认投入时才考虑；A / B 路线下前端可复用，不必重写 |
| 接入网易云非官方接口 | 会员曲目无直链、需维护登录态、有风控、接口随时失效；见 `M11` |
| 全量重写 | 现有代码已稳定运行并通过验证，重写会引入大量新缺陷而无对应收益 |
